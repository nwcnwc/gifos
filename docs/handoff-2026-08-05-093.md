### MEASURED 2026-08-05 (0.9.4 rollup work): the digest does NOT fix this jam

Fix-front item 2 above ends "this wants either frontier-aware descent or the V1
rollup digests (which carry per-subtree free-space — **the two fronts may be ONE
front**)." That hypothesis is now measured, and it is **REFUTED**. The digest
machinery landed (healing-laws § G, `test/sim/repro-digest.sh`), its free-space
fold carries both `freeC` (admissible frontier cells in a subtree) and `dmin`
(the shallowest depth in the subtree holding one), and the sim's `freemap` verb
reports both against ground truth. Sim-only, measured only — per G7 nothing
reads either field.

**At the plateau** (N=5000 det, the same 60k cap and the same 3076/5000 as
above, 1,924 seekers still churning):

| | |
|---|---|
| digest accuracy under the storm | root n = 3076 at ALL 3076 observers, `partial=0`, `mismatch=0` |
| free-space accuracy | digest 10,901 vs true 11,259 — **-3.2%, and conservative** (freeC excludes cells the holder believes soft-reserved) |
| agreement, per section | `hasRoom_agree=25/25`, `dmin_agree=25/25` |
| **spread of the TRUTH** | **`hasRoom_true=25/25`, `dmin_distinct=1`, best depth 2 for every section** |

**The hint is accurate and useless.** All 25 top-level subtrees have room, and
all 25 have it at depth 2. A seeker choosing a branch by `freeC` or by `dmin`
gets the *identical* answer from every branch it could pick. Accuracy was never
the binding constraint — *discrimination* is, and there is none to be had.

The FREEDEPTH line says why, and it is the important sentence: the free frontier
at the plateau is **327 @d2, 1196 @d3, 1174 @d4, 1194 @d5, 1135 @d6, 1227 @d7,
980 @d8, 1057 @d9, 977 @d10, 936 @d11, 1056 @d12** — 11,259 admissible cells for
1,924 seekers, ~5.9 each, spread almost evenly over every depth. **The storm
does not leave full branches next to empty ones; it leaves a uniformly HOLEY
tree.** That is precisely the shape in which "which branch has room" carries
zero information, at any level of the fold — so this is not an artifact of
measuring only the top 25 sections. The failure is INSIDE a branch: the descent
walks past shallow free cells into deep spines. Fix-front items 1 (heal-promotion
exclusivity) and 3 (the descent's pass-0 preference for firstHandLive hops
systematically following the BUSY branches) are therefore the whole of it, and
they are a descent/admission problem, not an information problem.

**What the digest DOES offer here, and it is not nothing:** a cheap, exact,
room-wide "there IS room" signal. Today a seeker that NOROOMs cannot distinguish
a genuinely full room from a jammed one, and neither can we from the outside —
the root fold makes that distinction free and correct even mid-storm (it was
exact at every one of 3,076 observers while 1,924 seekers thrashed). That is a
diagnosis and a UX signal ("the room is full" vs "we are still seating you"),
not a routing fix. Do not spend a session wiring free-space into the descent
expecting the plateau to move.

Forensic tools that exist now (all env-gated, committed): MESH_FINDLOG=<id>
(serving-side FIND decisions), MESH_SITLOG (vouch lifecycle), MESH_CELLLOG
(one cell's occ drops), MESH_DUPLOG (+DEEPADM/DEVOLVE/PHANTOMCLR-DEEP prints,
ADMIT_LOG prev+cur pair ledger), service verbs `holes` and `compact`.

## Addendum A: the stock-WebKitGTK lane — REFUTED at the root (2026-08-05)

Addendum 4 of the v4 handoff banked a route: Playwright's WebKit port joins a
mesh but never paints a remote tile and crashes on the app share, and that
smelled like PLAYWRIGHT'S EMBEDDER rather than WebKit — so drive the engine the
distro ships (WebKitGTK, what GNOME Web runs) through its own
`WebKitWebDriver`, where the `WEBKIT_FEATURES=WebRTCEncodedTransform` plumbing
that Playwright's fork lacks is supposed to work, and the pipe lane finally gets
a Safari-engine home on Linux.

**The two questions it was going to answer are unreachable: stock WebKitGTK has
no WebRTC at all.** `RTCPeerConnection` is `undefined`. So is `RTCDataChannel`,
`RTCSessionDescription`, `RTCIceCandidate`, `RTCRtpSender` and
`RTCRtpScriptTransform`. `MediaStream`, `getUserMedia`, `canvas.captureStream`
and `crypto.subtle` are all present — the hole is exactly and only the peer
connection, which is the whole mesh.

Measured three independent ways, because a single "it's undefined" always looks
like a flag somebody forgot to set (tool: `test/tools/webkitgtk-smoke.js`,
one command, no npm deps, its own probe server + Xvfb + driver):

1. **Runtime, through WebKitWebDriver**, with every documented knob set at
   once — `--enable-media-stream=TRUE --enable-webrtc=TRUE
   --enable-mock-capture-devices=TRUE` through `webkit:browserOptions.args`,
   plus `WEBKIT_FEATURES` in `browserOptions.env`. Undefined.
2. **The build census.** `libwebkit2gtk-4.1.so.0` links neither
   `libgstwebrtc-1.0` nor `libgstsdp-1.0` — *while `libgstwebrtc-1.0.so.0` is
   installed on the box*. That positive control is the load-bearing half: it
   turns "unavailable" into COMPILED OUT.
3. **The C API itself** (python3-gi): set `enable-webrtc` on a `WebKitSettings`,
   read it back `True`, evaluate JS in a real `WebKitWebView` — still
   undefined. The setting is a live property over a subsystem that was never
   built.

**Root cause, and it is not a packaging choice.** Upstream
`Source/cmake/OptionsGTK.cmake`:
`WEBKIT_OPTION_DEFAULT_PORT_VALUE(ENABLE_WEB_RTC PRIVATE
${ENABLE_EXPERIMENTAL_FEATURES})` — OFF for release builds — while
`ENABLE_MEDIA_STREAM` is `PRIVATE ON`, which is precisely the surface we
observe. Debian's `debian/rules` never overrides it. There is no distro to
switch to; a WebRTC-capable WebKitGTK has to be built from source with
`-DENABLE_WEB_RTC=ON`.

Environment facts banked (so nobody re-measures): sudo IS available on the
4-core box, no SUDO-UNAVAILABLE marker anywhere in this. Debian bookworm ships
webkit2gtk **2.50.6** — `webkit2gtk-driver` installs `/usr/bin/WebKitWebDriver`
cleanly, MiniBrowser lives at `/usr/lib/<triplet>/webkit2gtk-4.1/MiniBrowser`
and exposes every WebKitSettings property as a flag (`--help-websettings`).
Version 2.50.6 is far past the 2.42 the addendum worried about — the version
was never the problem. The whole fleet is the same story (the other Debian
boxes 2.50.6, the Ubuntu 22.04 one 2.50.4), and bookworm's WPE sibling
(`libwpewebkit-1.1-0` 2.38.6 + `wpewebkit-driver`) links no gstwebrtc either.
`WebRTCEncodedTransform` does not appear in `MiniBrowser --features=help` (472
features listed) — the feature plumbing is there, the subsystem it would gate
is not.

**Consequences, deliberately not fought:**

- **Ledger #5 (RTCRtpScriptTransform on a Safari engine) stays with real Apple
  hardware** — addendum 2's iPhone lane. On Linux the only engine that has it
  is Firefox, which is ALREADY a full mesh participant, so there is no gap
  worth building for.
- **Playwright's WebKit is not exonerated and not convicted.** The blank-tile
  and app-share-crash faults still have no second WebKit to compare against on
  Linux, and now provably cannot get one from apt. If that question is ever
  worth settling, the honest routes are a source build with
  `-DENABLE_WEB_RTC=ON` (hours, and gets a build nobody else runs) or real
  Safari on real Apple hardware (answers the question people actually care
  about). Prefer the second.
- The mesh smoke (one chromium host + one WebKitGTK guest) and the
  `WEBKIT_FEATURES` pipe lane were NOT built. Both need a peer connection to
  exist first; wiring them against an engine with none would have produced a
  harness that can only ever fail for an environmental reason — the exact
  shape of the dead suites the release-gate rule exists to prevent.

The tool is written for the day this changes rather than for today's answer:
`caps` goes green the moment a WebRTC-capable build appears, and `rtc` — a
loopback peer connection off a `canvas.captureStream`, asserting the RECEIVING
`<video>` reaches `readyState>=2` / `videoWidth>0` — is already the test
Playwright's WebKit fails. Decoding is not painting, and painting was the thing
that broke.
