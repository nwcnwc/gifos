## What this release is

**The provider release.** An app can now hand the WHOLE computer an ability
instead of keeping it to itself (docs/providers.md): a Provider app sits in the
Providers folder, is given a job in Settings → AI models, and every other app
that asks for that job gets it. Four shipped with it — Offline Text to Speech,
and three cheapest-text brains (BitNet, Gemma 3, Gemma 4) running llama.cpp in
wasm entirely on the device, weights riding the new gigabyte asset tier
(IndexedDB Blob store, hash-pinned, never in the GIF). Also: the graphing
calculator, minBuild floors, the steal-which-copy choice, sight words in Sound
It Out, the anyroad build-out, and the `?run=` link repaired.

**THE UNLOCK THIS CUT ACTUALLY DELIVERS:** the three provider brains declare
`minBuild: 1205`. The newest release before this was 0.9.5 at **build 1095**,
so on the default channel all three were unreachable — visible in the store and
impossible to run. 0.9.6 is build 1206. Every app in the catalog is now
installable on the current release; verified against the live catalog.

## Open, named, not done

- **`e2e-anyroad` should be SPLIT, not budgeted again.** 617s inside 900s is
  46% headroom, but it is one suite doing two full boots. Split the hills coda
  into its own file — the tier discovers files, so a new suite is gated the day
  it lands. The comment in `release.sh` says so.
- **`behavior.sh` does not start 8099 for 26a** (above).
- **The FLAKY list is the gate's weak layer.** Three different load-sensitive
  waits flaked across the two gates run this session: `e2e-video` and
  `e2e-vanish-browser` (first gate, both GREEN in the second) and `e2e-mosaic`'s
  stage-pixel liveness wait (second gate). Different suites each run is the
  signature of load sensitivity, not a regression — but it is the gate telling
  us its timing waits need work.

  **WORKED, same day — and one of them is now a PRODUCT lead, not a wait.**
  - `e2e-vanish-browser`: the gate never waited for the box to calm down before
    timing anything (`reap_browsers; sleep 1`, then straight into a suite
    asserting a 6s bound). `settle_box` now waits for the 1-minute load to fall
    below `nproc`, ceiling ~60s then proceeds and says so. 8ms on an idle box.
  - `e2e-mosaic`: rewritten to ask the product before the pixels — wait for the
    stage feed to exist in `feedsInfo()` and its decoded frames to CLIMB, then
    confirm paint. 4 green / 1 red since (green runs also dropped 201s -> ~90s).
    **The surviving red is not a wait problem.** With the new diagnostic, one
    run failed at two seats for two DIFFERENT reasons, one causing the other:
    P2 (mid-tree) held **two** `stg:` announcers and made **no claim**
    (`claims: ["sdrow:0","sub:0"]`), and P5 beneath it therefore never saw a
    `stg:` announcer at all (`ann: ["…|sdn"]`) while knowing the stage set and
    holding a healthy up-link. An announcer only becomes a candidate when its
    announced streamId resolves to a live incoming stream (`claimRedun`'s
    `live` gate) — so the lead is: why did BOTH candidates fail to resolve at
    P2, and why is there no recovery from that state? Everything below such a
    seat starves silently.

    **ROOT-CAUSED AND FIXED, same day.** `claimRedun` demanded a candidate HOT
    only if it was the primary or a waking standby. With NO primary both sets
    are empty, so every announcer for the slot was sent **mx-IDLE** — "park it,
    I don't want it". The sender parks (`replaceTrack(null)`), the stream never
    lands in `p.incoming`, the candidate never goes `live`, the first-claim
    path (`cand.find(x => x.live)`) never fires, there is still no primary, and
    the next sweep sends idle again. **A seat that has not claimed yet actively
    guarantees it never will**, and nothing in the loop ever asks again.

    It hides because a fresh ship starts ACTIVE at the sender, so the track is
    normally already there when the announce lands; it bites when the track is
    LATE (announce ahead of renegotiation) or was parked by an earlier idle —
    and then it is PERMANENT. The fix demands ONE candidate hot when a slot has
    no primary, chosen deterministically (shortest announced chain, then peer
    id). The ONE-PIPE law is intact: one entry, only while there is no primary.
    Guarded by the invariant itself in `e2e-mosaic` — a slot with candidates
    and no claim must be demanding one of them hot — sampled over a WINDOW,
    because the unclaimed moment is the transient the bug lives in.

    **MUTATION-TESTED BOTH DIRECTIONS** (nvidia-laptop, interleaved A/B/A/B,
    arm B = the fix reverted in a scratch `run.html`):

    | arm | fix | result |
    |---|---|---|
    | A | present | PASS, `judged: 2` |
    | B | reverted | PASS, `judged: 0` — VACUOUS, state not reached |
    | A | present | PASS, `judged: 1` |
    | B | reverted | **FAIL**, `judged: 3`, violation below |

        {"seat":"P4","slot":"sgs","announcers":1,
         "demands":["k_0cbd05…|sgs|21f5f876-…=i"]}

    One announcer for `sgs`, no claim, and the only demand is `=i`. That is the
    deadlock caught in the act. Note arm B's first sample passed VACUOUSLY —
    which is why the check now counts and prints the observations it judged: a
    run that never met an unclaimed-but-announced slot has not exercised this
    invariant and must not score a silent green.

    One false positive was found and fixed along the way: the guard originally
    asserted the invariant for EVERY slot and red-ed on `sdnm:1_1_0` in a
    healthy room. Only `isRedun` slots (sdm/sdx/sdn/sgs/stg:*/sdrow:*) have
    their demand decided by this hot set; `sdnm:` rides the mx-want relay.

## Process notes paid for this session

- **penguin has NO playwright chromium at all** (ffmpeg/firefox/webkit only), so
  every browser tier scores DEAD there. It is Nathan's personal machine: edit
  here, compute elsewhere.
- **A half-built stack reds exactly like a product bug.** A standalone
  `e2e-video` run failed at 90s waiting for a P2P data link because the
  scaffolding started the site server but not relay-local. The suite was fine.
  Start the stack the gate starts, or do not believe the red.
- **Concurrent sessions push to main mid-gate.** Two provider commits landed
  during the first gate and moved product code (`site/js/runtime.js`),
  invalidating that gate for certification. A cut needs a quiet tree — re-check
  `git rev-list --count HEAD..origin/main` before trusting any gate result, and
  re-check it again immediately before cutting.
- **Poll remote long-runs with a remote `until` loop, not a local one.** A local
  poll returns in seconds and burns turns without advancing the job.
