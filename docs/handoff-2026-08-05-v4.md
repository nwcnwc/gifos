## Addendum 4: the RTCRtpScriptTransform-on-Linux hunt (Nathan's instinct was right)

The API IS in the Linux port — measured: `libwebkitgtk-6.0.so` in webkit-2336
(Playwright 1.62.1, latest) contains the full implementation AND the runtime
preference key `WebRTCEncodedTransformEnabled`. What blocks it is PLAYWRIGHT'S
EMBEDDER: their driver sets its own fixed WebKitSettings and exposes no
feature-flag hook; the stock-WebKitGTK `WEBKIT_FEATURES` env plumbing is not
compiled into their fork (no such string in the binary — tested empirically,
env route inert). Upgrading playwright does NOT help (1.61.1/webkit-2311 and
1.62.1/webkit-2336 both gated off).

The viable Linux route, banked not built: STOCK WebKitGTK + its own
`WebKitWebDriver` (Debian: webkit2gtk + the driver package; stock builds
honor `WEBKIT_FEATURES=WebRTCEncodedTransform` and MiniBrowser `--features`).
That means a WebDriver/selenium harness variant for the pipe suite, not
Playwright. Two unknowns to measure before investing: (a) whether the GTK
port's GStreamer-WebRTC backend implements the transform FUNCTIONALLY
(symbols compiled != frames flowing), (b) Debian bookworm's webkit2gtk
version vs the 2.42+ features plumbing. If both check out, e2e-pipe gets a
real Safari-engine lane on Linux; if not, the pipe-on-Safari question stays
with real Apple hardware (addendum 2's iPhone lane).

Fleet state: webkit+firefox playwright builds installing on nvidia-laptop /
clawbox / pi-16gb / raspberrypi (results in /tmp/browsers-install.txt per
box; deps need sudo — check for SUDO-UNAVAILABLE markers). penguin already
has webkit-2311, webkit-2336, firefox-1532 + host deps.

## Addendum 6: the multi-engine GATING MEASUREMENT, answered (2026-08-05)

Addendum 3 said: measure whether a WebKit and a Firefox participant complete a
mesh join before wiring any battery scenario. Measured, both engines, 2-party
rooms against the local stack, judged from BOTH sides. Tool:
`test/tools/engine-smoke.js` (`APP=1` adds the app-share lane, `DIAG=1` the
media forensics); `meet.js` gained `--engine chromium|webkit|firefox` and
`--init-script <file>`.

**FIREFOX (firefox-1532 / Firefox 151): FULL PASS.** Seat, links, mutual
roster sight in ~6s, live video BOTH ways, DC gossip both ways, chat over the
DC lane, and the guest mounted a host-shared app in 5s. No H.264 in the
playwright build (VP8 is what a firefox↔chromium call negotiates); it DOES have
`RTCRtpScriptTransform`, which playwright's WebKit port does not — a second,
unexpected Linux home for the pipe lane. `isMobile` is unsupported for firefox
in playwright, so `--profile phone` drops that property only.

**WEBKIT (webkit-2311, Safari 26.5 engine): JOINS, NOT A FULL PARTICIPANT.**
Control plane perfect and repeatable (seat, links, mutual sight, DC gossip,
chat). Two hard limits:
1. *Remote tiles never render.* getStats shows inbound H.264 arriving AND
   decoding (framesDecoded climbing, frameWidth/Height set) while the tile's
   `<video>` stays readyState 0 / videoWidth 0 and `play()` never settles.
   Refuted: not autoplay (muted+playsInline, play already called), not the
   silent audio track (a video-only re-point changed nothing). Its local
   preview plays and chromium peers DO see its video — a working sender and
   decoder that cannot paint a remote MediaStream. So a WebKit role may assert
   control-plane/DC facts, and may be the peer someone else observes, but must
   never be the OBSERVER of video liveness.
2. *The app share kills it.* ~5s after a host runs an app into the room the
   WebKit web process CRASHES. Reproduced twice, with and without probes.

Confirmed as designed: `GifOS.meshPipe.supported()` is false on WebKit (and on
the Chrome 137 host) — the pipe lane self-disables correctly, nothing to fix.
Neither engine ships a fake capture device (gUM fails
OverconstrainedError/NotFoundError), so the injected canvas-captureStream
camera is REQUIRED off chromium — it carries across all three unchanged.
