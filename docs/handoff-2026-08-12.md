## 2. The behaviour box: a resident model is not spare capacity

`ps` accounted for ~500 MB of 7.6 GB; `MemAvailable` said **49 MB**. The missing
6.5 GB is a resident GPU LLM service — on a unified-memory board the GPU's
memory IS system memory, held through nvmap, so it appears in no RSS at all.
`free` and `top` both look innocent. (The box fact was already known and
recorded on 2026-08-06; what was new is that this was the flake, and that the
harness now refuses instead of manufacturing reds.)

## 3. Chess: the board rebuilt itself under your finger

`#fBoard.innerHTML = ''` plus 64 fresh divs on EVERY render — and it renders on
the presence beat (`HB_MS = 3000`, plus each peer's own beat, so ~2 rebuilds per
3s), not only when the position changes. On a loaded phone a finger that goes
down just before a rebuild lifts over a node that no longer exists and **the move
is silently lost**; it is also why e2e-chess-mp red-ed the 0.9.7 gate twice
(Playwright will not click an element that was not stable across two animation
frames). **v1.0.1** paints both boards in place — `boardCells()` builds 64
squares once, `paintSq()` writes only what differs, the tap handler reads the
square's CURRENT coordinates so flipping for Black replaces nothing, and the
piece is a text node so it can share the square with the marker and coord spans.

Guarded at the END of e2e-chess-mp (sampling before the moves adds a settle onto
a startup-race window this suite once masked): in a 4s window the renders must
ADVANCE while `#fBoard` sees **zero** childList mutations. Measured
`{muts:0, renders:4, kept:true, squares:64}`. Mutation-tested: restore the
rebuild and the check fails AND all four moves fall back to a forced click,
which now says so out loud.
